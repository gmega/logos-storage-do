We are updating this harness to Logos v0.4. We'll need to make a few changes:

## Use Service Discovery

Since [#1582](https://github.com/logos-storage/logos-storage-nim/pull/1582), we now have service discovery available. This means we no longer need to specify dht-proxy and mix relays separately - after bootstrap, the system should learn about providers for those services from the network itself. It'll also learn about AutoNAT and Circuit relay providers. We need to remove all hardcoded configuration for those from the deploy.

At the same time, we need to ensure that their service discovery tables are populated. We'll have a [Dashboard](#Dashboard) for this.

## Use Precompiled Builds

We will use the new devnet binary builds (https://hackmd.io/MD_DGbjYRj2eHamGYEQdBA - use Kody, you have access to the HackMD API from it) to deploy the module, so we can save time during deploys. You should deploy the latest version currently in that repo. You should refuse to deploy if the version being deployed is the same as the one already deployed, but there should be an override switch for redeploying anyway. The version deployed should appear in the deploy bucket metadata (under a global "version" key).

## Dashboard

You should set up a simple dashboard in Digital Ocean under basic auth that shows node health. Figure out a way to generate a password so you don't have to read the file, ever. The password should be on disk and I should be able to cat it. Node health should show what's under the `logosctl call storage_module debug` endpoint. Feel free to get creative to show that info nicely.

## Dashboard v1.1

Add a "file panel" with two entries and three buttons to each node.

* entries refer to files available for download (random file, farewell to westphalia).
* entries should be selectable.
* button allows either direct download, or download over mix for the selected file.

When the user clicks "download" (using mix or direct), the dashboard should:

1. download the selected file using the node;
2. copy the file locally and stream the contents to the user browser so they can see the file.

The entry should have an indicator (e.g. little "dot light") that's either red if the node does not have the file, or green if it has (you'll need to list the manifests, it's an imperfect indication but it's what we've got).

The delete button removes the file from the local node and it's back to red. It should be disabled in at least one of the storage nodes (RS-1, I suppose) or the user might screw up and delete it from everywhere.

## Agent Notes

Implementation and deployment completed on 2026-11-24.

### Deployment and runtime

- All six nodes (four MP, two RS) were deployed with module
  `3.0.2-397.gc3732212`, running libstorage `0.5.3-cf4c901a`. All four discovery
  tables (Mix, DHT proxy, AutoNAT and circuit relay) were populated.
- `scripts/deploy.sh` resolves the latest published Linux module, verifies its
  checksum and refuses the already-deployed version unless passed `--force`.
  The successful deployment version is published at the bucket root in
  `metadata.json`; bootstrap records are under `v0.4/`.
- The portable CLI is pinned to 0.3.2. Its bundled storage and package-downloader
  module directories are moved aside during provisioning: otherwise the CLI
  can automatically start the bundled storage implementation instead of the
  installed module. The CLI-reported version alone is not reliable evidence of
  the running libstorage revision; inspect `debug` and the installed release.
- Bootstrap configuration uses an empty `bootstrap-node` list, not the removed
  `no-bootstrap-node` option. Other nodes receive only bootstrap SPRs; provider
  lists are discovered dynamically.
- When rebuilding upstream, explicitly select the intended storage module ref.
  A build with a blank ref previously built master rather than the desired
  submodule revision. The deployed release includes the `serviceProviders`
  debug API; earlier builds supported discovery without exposing its tables.

### Dashboard behavior and operations

- Dashboard: <https://138.68.101.41/>. At the user's request, basic auth was
  removed after the original specification. HTTPS currently uses a self-signed
  certificate; the local verification certificate lives in ignored
  `scripts/.dashboard/server.crt`.
- Each node has the same two file entries, catalogued from RS1's manifests and
  source checksums. Presence compares CIDs, not filenames. Independently
  generated random files on other nodes can therefore show absent for RS1's CID.
- Direct and Mix downloads use `downloadToUrl`. Mix sets `isPrivate=true` and
  `advertise=false`. Existing cached data can satisfy either mode, so choosing
  Mix does not prove that fresh network traffic traversed Mix.
- The node polls output-file size every two seconds and reports progress over
  SSH stderr, separately from file bytes. Both node and dashboard verify SHA-256.
  The download tab shows node progress, verification and dashboard-copy stages;
  PDFs open inline and the random binary is offered as an attachment.
- Delete waits until the CID disappears from manifests. RS1 is protected in both
  the API and the forced node command. Confirmed deletion updates the indicator
  immediately and overrides older snapshots until a newer snapshot is collected.
- Diagnostic dropdowns are grouped under **Detailed status**, initially collapsed;
  its expanded state survives automatic dashboard refreshes.
- Snapshot collection runs every 30 seconds. File jobs run in a separate
  `logos-dashboard-files` service. The dashboard account is unprivileged, uses
  pinned SSH host keys and can invoke only the forced snapshot/file commands.
  No arbitrary CID, path or shell command is accepted from browser requests.
- Public file operations still consume resources: limits are two running jobs,
  one per node, eight retained jobs, six submissions/minute/IP and four concurrent
  API requests limited to 1 MiB/s each. These are abuse limits, not a billing cap.
  No DigitalOcean provisioning credentials are required on the dashboard host.
- File links expire after 15 minutes. Restarting the file API loses its in-memory
  job registry and clears cached dashboard copies. Wait for active transfers
  before restarting it. Static HTML updates do not require a service restart.
- Reapply dashboard configuration with `ansible/dashboard-playbook.yml` and the
  resolved release variables, as documented in README. Logs are available via
  `journalctl -u logos-dashboard` and `journalctl -u logos-dashboard-files`.
